# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Web app (side panel + dashboard pages served by the backend) + local FastAPI backend that scores any chatbot's answers with DeepEval metrics using a separate judge model (OpenAI-compatible API, Groq by default). `docs/WORKFLOW.md` describes request flows end to end; `docs/superpowers/specs|plans/` hold the design docs.

## Commands (Windows, run from repo root)

```bat
run-backend.bat                                              :: creates .venv on first run, serves http://127.0.0.1:8765
update-packages.bat                                          :: run by both start scripts: upgrades to newest versions requirements.txt allows, smoke-tests, rolls back on failure (JUDGE_AUTO_UPDATE=0 skips; skips while 8765 is served)
.venv\Scripts\python -m pytest                               :: offline suite, no judge tokens (what CI runs)
.venv\Scripts\python -m pytest -m smoke                      :: fast wiring checks
.venv\Scripts\python -m pytest tests/test_app.py::test_name  :: single test
node --test tests/js/report.test.js                          :: PDF report JS tests (also run by pytest via tests/test_report_js.py; skipped without Node)
```

Live metrics against the real judge (spends tokens): `set RUN_LIVE_JUDGE=1`, then `.venv\Scripts\python -m pytest -m live`.

- Config comes from `.env` (see `.env.example`): `JUDGE_API_KEY` (required), `JUDGE_MODEL`, `JUDGE_BASE_URL`, `JUDGE_DB_PATH`, `JUDGE_LOG_LEVEL`, `JUDGE_MAX_BODY_MB`, `JUDGE_CONCURRENCY`, `JUDGE_METRIC_CONCURRENCY`.
- `pytest.ini` disables the globally installed deepeval/opik/langsmith pytest plugins; keep that.
- No linter/formatter is configured. CI (`.github/workflows/ci.yml`) runs the offline suite on Python 3.13; the live job is manual-dispatch only.
- The web app has no build step: start the backend and open `http://127.0.0.1:8765/` (or run `start-llm-judge.bat`; see `ChatbotExtension/README.md`). Hard-refresh (Ctrl+Shift+R) after editing its files. There is no Chrome extension any more (the folder keeps its old name).

## Architecture

- **`backend/dashboard/app.py`** — the whole HTTP API. At import it opens SQLite (`storage.init_db`, which also migrates legacy target configs). No CORS middleware (the web app is same-origin, so every other origin is refused) and `TrustedHostMiddleware` only `127.0.0.1`/`localhost` — deliberate (protects stored target API keys); don't add CORS for `*`.
- **`backend/metrics_catalog.py`** — single source of truth for metrics. Each `MetricSpec` bundles the DeepEval metric builder, how to build an `LLMTestCase` from a golden row + reply, the dataset (`goldens` or `goldens_with_context`), and `needs` (reference data required for ad-hoc judging). 45 specs in 8 groups plus "custom" (`GROUPS`; "agent" and "reference" hold the agent metrics and the no-judge text-match scorers in `backend/text_match.py`); each has `direction` ("higher"/"lower"), a default `threshold`, `presets()` per environment (`ENVIRONMENTS`), and `kind` ("single"/"conversation"). Scores are DeepEval's own: hallucination, bias, toxicity and pii_leakage are "higher" too (DeepEval 4 scores them 1 = clean; `storage._migrate_deepeval_scale` moved old runs once, `ui.js` moves saved thresholds once). "lower" remains only for user-made violation-rate metrics, via `deepeval_threshold`/`reported_score`. A job sends each question once: `targets/shared.SharedReplies` (per job in `app._job_clients`) gives every metric the same reply, as DeepEval scores one test case with many metrics; `multi_sample` and `attack` specs use `.fresh`. Jobs may carry `deepeval` {strict_mode, include_reason, async_mode} (`metrics_catalog.apply_deepeval_options`; strict sets threshold 1). Judge consistency, the latency limit and `check_replies` are opt-in extras, not DeepEval. `/api/run` and `/api/judge` take the per-metric `threshold` the side panel stores in `localStorage` (`llmJudge:thresholds` {key: value}, `thresholdEnv`). As in DeepEval, each case passes on `metric.is_successful()` and a run passes only when every case passes (`cases_passed`, `pass_rate` in the result; the average is shown, not gated). Metrics a job cannot run (not applicable, or no case in the golden set) are kept as `options.skipped` [{key, title, reason}] (`app._skip_reason`, also `skip_reason` in `/api/metrics`) and shown by scans and the report. Conversation scenarios: shipped in `conversations.default.json`, edited copy `conversations.json` (gitignored, reset with the goldens on every panel load, CRUD at `/api/conversations`). Security probes (9 red-team G-Eval metrics incl. `harmful_content`, group `security`): shipped in `security_probes.default.json`, edited copy `security_probes.json` (gitignored, reset together with the goldens, CRUD at `/api/security-probes`); a target's optional `persona` goes into each probe's context, and its `probe_set` (`generic` default, or `ecommerce`) picks which probes are sent. The same store holds adversarial prompts for `bias`, `toxicity` (dataset `safety_probes`: probes first, then the goldens) and `no_prompt_leak` (dataset `prompt_leak_probes`: probes only); `security_probes.PROBE_METRICS` lists every metric a probe may name. Every spec also carries dashboard card copy (`ui_category`, `scale_hint`, `question`), and `/api/metrics?target_id=` adds `cases_available`; specs that score `retrieval_context` use the chatbot's own (target `context_path`) and otherwise fall back to the golden's context, with each row's `context_source` = "golden" and the result's `note` saying so. Each spec's `scores_on` / `criteria` feed the dashboard; result rows carry `input`, `actual_output`, `expected_output`, `context`, `context_source`, `score`, `passed`, `reason`. Both the API and the tests import from here. Run-time applicability (see docs/WORKFLOW.md "Metrics that switch on at run time"): `MetricSpec.applies(features, items)` (features = target has `context_path` / `tools_path`) makes a metric `unavailable` in `/api/metrics` and an error run that sends nothing; `skip_before` / `skip_case` / `not_applicable` leave single cases out (`runner._NotApplicable`, result `cases_not_applicable`). Turn RAG metrics read each turn's `retrieval_context` (kept by `runner._run_conversation`) or a scenario's optional `context`; Prompt Alignment's `instructions` come from `targets/instructions.resolve` (via `metric_options`): typed on the chatbot, else the captured request's system prompt, else standard production rules (`BASE_RULES` + `RAG_RULES` / `AGENT_RULES` / a role rule when the chatbot has `context_path` / `tools_path` / `persona`); the run's `note` names the source. A target's optional `sources_fallback` (`knowledge_base`: BM25 over the theme's uploaded documents; `cited_links`: public pages the reply links to; `backend/rag/derived_sources.py`) supplies `retrieval_context` when the response has none, for every spec except `grades_retriever` ones (Contextual Precision / Recall / Relevancy and their Turn versions); rows get `context_source` `knowledge_base` / `cited_pages` (docs/WORKFLOW.md "Sources the app finds itself"). Agent metrics read `ChatReply.tools_called` (target `tools_path`, parsed by `curl.tool_calls`) and goldens' optional `expected_tools`. Auto-discovery (docs/WORKFLOW.md "Paths found during scans"): `HttpTargetClient.discovered` collects tool / source paths seen in replies (JSON or stream) that the target has none saved for; `app._save_found_paths` saves them (never over a typed path) and `app._after_job` (the `JobQueue` `after_job` hook) stores them in `jobs.discovered` and queues one follow-up job of the metrics they switched on (`app._availability`, same check as `/api/metrics`), options + `auto_discovered`; scans get a `note`. Pairwise jobs are not watched.
- **`backend/dashboard/runner.py`** — `run_spec` sweeps a theme's goldens against a target and stores **one** aggregated row per run (charts plot run averages); `limit` (the dashboard's cases per run) caps the cases sent and `persona` feeds the security probes; cases run on `case_workers` threads (`JUDGE_CONCURRENCY`, default 4, also the judge's cap on calls in flight; conversations, attacks and targets with `send_delay` stay serial), each thread with its own metric instance, rows kept in case order; `_case_slots` caps cases in flight across all runs at `JUDGE_CONCURRENCY` (tests pin it and `jobs.METRIC_CONCURRENCY` to 1 via the `serial_cases` fixture); `judge_one` scores a single ad-hoc answer and persists nothing. Each run also records how it was judged (`judge_model`, `judge_tokens`, `judge_calls`, `target_calls`, `duration_s`, `judge_spread`: columns added by `storage.RUN_EXTRA_COLUMNS`, counted by the run's own `usage.meter()`, a contextvar that worker threads get through `contextvars.copy_context()`, so runs side by side don't mix) and notes a judge model change since the previous run; `check_consistency` (`/api/run`, side-panel setting `checkConsistency`) scores every reply twice, averages, and flags `judge_unstable` when the widest gap passes `UNSTABLE_SPREAD` (0.15). Failures come back as `status: "error"` dicts, not exceptions. Runs from the web app go through `backend/dashboard/jobs.py`: `POST /api/jobs` queues a batch (one job at a time on a worker thread, reusing `run_spec`; up to `JUDGE_METRIC_CONCURRENCY` (default 2) of its metrics run side by side (a job's `metric_concurrency` option, 1–8, overrides it: the web app's "Parallel metrics" select, bounds from `GET /api/run-limits`; "Run mode" is the saved `casesPerRun` sent as `limit`), pairwise jobs one at a time; `current` is the first running metric, `running` lists all), `GET /api/jobs/{id}` reports progress and results, unfinished jobs become `interrupted` on start, the web app's Stop calls `POST /api/jobs/cancel-all` (every queued/running job of every chatbot; `backend/cancel.py` contextvar check makes `HttpTargetClient.send` and `GroqJudge._call` raise `RunCancelled` before their next call, and a stopped job queues no auto-discovered follow-up), and each run's full result is stored in `runs.result_json` (returned as `result` by `/api/runs/latest`). Tests set `JUDGE_START_JOB_WORKER=0` and call `jobs.process_next()` themselves.
- **`backend/targets/`** — one connector, `HttpTargetClient` (type `http`): replays a request captured from the chatbot's website. `presets.py` builds that same config for an OpenAI-compatible LLM (`POST /api/targets/parse-llm` → url/headers/`messages` body, reply at `choices.0.message.content`), so `pytest -m live` can judge another model without a capture; the side panel's "Or fill from an LLM API" fills the chatbot form with it. Config is `{url, method, headers, body_template, response_path, theme}`; `{{message}}` marks where the question goes (JSON-escaped in bodies, URL-encoded for form bodies/URLs). Replies come from a JSON path, from SSE `data:` events joined at that path, or as raw text when the path is empty. `curl.py` turns "Copy as cURL (bash)" into that config (`/api/targets/parse-curl`); `/api/targets/test` tries an unsaved config. Header values (cookies, keys) are masked as `***` in responses, and a PUT without `headers` keeps the stored ones. Optional `max_message_length` (longer messages raise `MessageTooLong`; the runner skips those cases and passes `max_chars` so Summarization cuts its source to fit), `send_delay` (seconds between messages, enforced per chatbot URL across clients and threads via `_PACES`), and `check_replies` (default false, opt-in: `reply_check.service_message` turns replies like "limit reached" / "please log in" / empty into `ChatbotUnavailable`, a run error that records nothing). 429/503 are retried 3 times; 401/403, timeouts and refused connections get plain messages. The canned-answer chatbot used by tests lives in `tests/fakes.py`, not in the product.
- **`backend/judges/judge.py`** — wraps the judge as a DeepEval `LocalModel` with rate-limit retries. The judge must never be the chatbot under test.
- **`backend/traffic.py`** — console traffic log (`llm_judge.traffic`, on unless `JUDGE_LOG_TRAFFIC=0`): `HttpTargetClient.chat` logs each question/reply, `GroqJudge`'s wrapped `create` logs each judge call (prompt size, time, tokens, output) and sets a 90 s per-call timeout (`JUDGE_TIMEOUT_S`; without it a hung call stalled runs ~30 min), `jobs.py` logs metric start/finish. Text is clipped to 300 chars; headers/keys never logged. `hardening.configure_logging` also writes the `llm_judge` logs to `logs/traffic-YYYY-MM-DD.log` (`JUDGE_TRAFFIC_FILE`, empty = off; tests set it empty), which `watch-traffic.bat` tails, however the backend was started.
- **`backend/usage.py`** — in-memory judge token / call counter (`GroqJudge.load_model` wraps the OpenAI client once; `HttpTargetClient.send` counts chatbot calls), served at `/api/usage` and reset with the process or `POST /api/usage/reset`.
- **Goldens** — `backend/datasets/goldens.json`, grouped by theme (`generic` default: bot-agnostic; behaviour-style answers plus grounded goldens whose `context_in_prompt` makes `metrics_catalog.ask` send the facts with the question; `general_support` is the ShopEasy shop set), edited through the API/side panel. `goldens.json` is runtime state: like `conversations.json` and `security_probes.json` it is seeded from `goldens.default.json` on first use (`goldens._read_all`) and git-ignored. Edits are session-only for shipped themes: the side panel calls `POST /api/goldens/reset` on every load, which restores the themes in `goldens.default.json` (the defaults to edit) and keeps other themes. Every write goes through `_write_all`, which appends what changed and the calling function to `goldens_changes.log` next to the file (gitignored); `shipped_health()` / `GET /api/goldens/health` counts missing shipped rows, which the side panel reports. The autouse fixture in `tests/conftest.py` redirects `GOLDENS_PATH` to a copy of `tests/data/goldens.json` for every non-smoke test.
- **Document → goldens (`backend/rag/`)** — `POST /api/documents/url {theme, url}` fetches a help page (`fetch.py`: http(s) only, 5 MB cap, stdlib HTML-to-text, refuses pages under 200 chars) and feeds its text through the same generator. `POST /api/documents` saves the upload under `backend/datasets/documents/<theme>/`, runs the DeepEval `Synthesizer` (judge as critic, local sentence-transformers embedder in `embeddings.py`), and appends goldens. `app.py` imports this lazily inside a wrapper named `generate_goldens_from_document` because `sentence_transformers` takes ~40s to import. Keep it out of module-level imports and keep the wrapper name: tests patch `app_module.generate_goldens_from_document` and `backend.rag.embeddings.SentenceTransformer`. A new chatbot's dataset is built by `POST /api/targets/{id}/prepare-goldens` (side panel, after the user says yes with `generate: true`): own theme + starter goldens, then `backend/datasets/autogen.py` interviews the chatbot (`INTERVIEW`), searches its site for FAQ / help / docs pages when no `help_url` is given (`find_help_pages`: Origin/Referer, the chatbot host and its main domain × `HELP_PATHS`, max 12 fetches; sets `docs_searched` and `help_url`), queues found pages through the document pipeline, and has the judge write goldens (`source: "auto_chatbot"`) and conversation scenarios fitted to it (`write_dataset`). Each step runs once per chatbot.
- **Storage** — `backend/storage.py`, SQLite tables for targets, runs, documents, jobs, `pairwise_runs` and `human_labels` (busy timeout 10 s). New run columns go in `RUN_EXTRA_COLUMNS` (nullable, additive): `latency_p50`, `latency_p95`, `judge_cost_usd` were added that way. Fresh sessions: each panel load calls `POST /api/session/start` (returns the max run id) and stores it as setting `freshSinceRunId`; scores, trend, cases and the report pass it as `since_id` (the report and the dashboard's Details read cases only from `runs.result_json`, no browser copy) to `/api/runs/latest` / `/api/history`, so they start empty while every run stays stored. The dashboard's History view lists scans (see Scans) rather than single runs, and deletes them all at once (`DELETE /api/targets/{id}/runs`, runs and finished jobs; `DELETE /api/runs/{id}` still removes one run); deletes broadcast setting `runsChangedAt` so open views reload.
- **Roadmap features (Advanced tools page, `ChatbotExtension/advanced/`)** — all additive; runs without the new options behave as before. `MetricSpec` gained `settings` (tunable knobs passed to `build_metric` via `metrics_catalog.metric_options`), `needs_target` (target config fields, e.g. Prompt Alignment's `instructions`; a run without them is an error), `runner_settings` (knobs the runner reads instead) and `variants` (kind `multi_sample`: Robustness / Self-Check send several messages per golden). Spec kinds: `single`, `conversation`, `attack` (Multi-turn Jailbreak: `runner._run_attack`, the judge writes each escalating turn), `multi_sample`. Custom metrics (`backend/datasets/custom_metrics.py`, G-Eval or DeepEval DAG JSON, `custom_` keys) are NOT reset on panel load; `metrics_catalog.get_spec` / `all_specs` include them (app.py keeps `SPECS_BY_KEY` first because tests patch it); DAG "metric" children and per-node models are refused (`check_dag_safety`). `run_spec` also takes `enhancements` (`backend/datasets/attack_enhancers.py`, probe datasets only, never written back), `max_latency_s`, `price_per_mtok` (meta `judge_price_per_mtok`, `/api/judge/price`) and `calibration_examples` (human labels appended to G-Eval criteria); results add `stats`, `latency`, `judge_cost_usd`, `by_enhancement`, rows add `golden_id`, `latency_s`. Free-form judge prompts go through `backend/judges/ask.py`. Other modules: `dashboard/compare.py` (`/api/runs/compare`), `dashboard/pairwise.py` (A/B with position swap, job kind `pairwise` in the same job queue), `redteam_coverage.py` (OWASP + risk categories), `datasets/simulator.py` (`/api/simulate`), `export_suite.py` (`/api/export/suite` zip; header values never exported), `rag/generate.py` `synthesizer_configs` (evolutions/filtration/styling; names in `rag/generation_options.py` so the app never imports sentence-transformers at startup), golden drafts (`status: "draft"`, skipped by `MetricSpec.cases`, `/api/goldens/review`), calibration (`/api/calibration`). Front end: `ui.js` `runOptionsBody` adds the saved `runOptions` setting to every job.
- **Production guard rails** — `backend/dashboard/hardening.py`: outermost middleware (body limit `JUDGE_MAX_BODY_MB`, security headers, `Cache-Control: no-store` on `/api`, request log of paths and status only at `JUDGE_LOG_LEVEL`), JSON 500 handler without tracebacks, and `/api/health` (503 when SQLite fails). CI also syntax-checks the web app JS and runs an informational `pip-audit`; Dependabot opens weekly update PRs.
- **Scans** — `backend/dashboard/scans.py`: every non-pairwise job of a chatbot is one scan, numbered 1, 2, … per chatbot (`storage.target_jobs`), with one overall `result` (passed / failed / incomplete / running / queued), counts and an average where "lower" metrics count as 1 − score. `GET /api/targets/{id}/scans` (newest first), `GET /api/scans/{job_id}` (with every metric's result and `run_options`: limit, metric_concurrency, deepeval, … from the job); each scan also carries `metric_scores` [{key, score, status, direction, std, cases}] (std = population std of the case scores), `GET /api/scans/{job_id}/compare?with=` (per metric: better / worse / same / new / removed) and `GET /api/scans/{job_id}/cases?with=` (per test case, for the Regressions page), `DELETE /api/scans/{job_id}` (one finished scan: `storage.delete_scan` drops its job and the target's runs of its metrics stamped inside the job's start–finish window, since runs carry no job id; 409 while queued/running). `storage.clear_runs` (History's Delete all) also deletes the chatbot's finished jobs, so their scans go too.
- **Web app** — `ChatbotExtension/` (old name, kept): `sidebar/` (main UI), `dashboard/` (chat, trend/latest charts, Scan history), `report/`, `advanced/`, and three pages opened from Scan history in new tabs: `scan/scan.html?job=` (one scan in full: overall result, facts, metric table, every metric's cases), `runs/runs.html#evaluation|#home|#overview|#cases|#compare?target=&job=&with=` (test runs, laid out like Confident AI: Evaluation = every run with a date range, a per-metric chart with ±1 std error bars, % trends and a runs table with metric pills; Overview = properties, segmented results dial, run settings, radar and Histogram / Average / Median / Breakdown; Test Cases with filters, column picker, per-metric tabs; Evaluation also deletes ticked runs one by one; Test Cases' "Save as new dataset" posts the shown cases to `POST /api/goldens` under a new theme (expected answer = the case's, else its reply); the radar plots every metric (names on hover past 12) with a category picker; Compare = two runs' donuts, overlaid histograms and cases side by side, matched by golden or input. Charts use the dataviz reference palette `--s1..--s8`; dials use `.dial` because `skin.css` owns `.ring`) and `regressions/regressions.html?job=&with=` (two scans case by case: improved / regressed / new / removed). `lib/api.js` (backend client, calls its own origin). Look: `lib/theme-mode.js` (in each page's `<head>`) sets `data-theme` on `<html>` from `llmJudge:theme` (dark by default; any `button.theme-toggle` flips it, synced via the `storage` event); pages' dark tokens sit under `:root[data-theme="dark"]`, and `lib/skin.css` (loaded after each page's CSS) adds the dark skin: slate with terracotta accent on every page (side panel `body.panel` differs by layout only), flat (no gradients or glows), score rings (`.ring`, `--pct`) and the pass/fail `.donut`. Files under `/app` are served with `Cache-Control: no-cache` (`hardening.py`), so edits show on a normal reload. The backend serves it at `/app/` (`/` redirects there; `index.html` shows panel + dashboard side by side in iframes). `lib/ui.js` `settings` keeps state in `localStorage` (`llmJudge:<key>`) and syncs the panes via the `storage` event; finished runs show as browser `Notification`s plus a tab-title mark.

`01_Chatbot_Shopeasy_chatbot/` is a separate sample chatbot app used as a judging target, not part of the judge. It is committed without secrets: its real `.env` is gitignored and `.env.sample` holds placeholders only.
