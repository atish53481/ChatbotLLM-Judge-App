# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Web app (side panel + dashboard pages served by the backend) + local FastAPI backend that scores any chatbot's answers with DeepEval metrics using a separate judge model (OpenAI-compatible API, Groq by default). `docs/WORKFLOW.md` describes request flows end to end and `docs/workflow.html` draws them (published at https://claude.ai/artifact/JxkuyFH5iLH8ZdzoszZ4Qv); keep both current (see "Keeping the docs current"). `docs/superpowers/specs|plans/` hold the design docs.

## Commands (Windows, run from repo root)

```bat
run-backend.bat                                              :: creates .venv on first run, serves http://127.0.0.1:8765
update-packages.bat                                          :: run by both start scripts: upgrades to newest versions requirements.txt allows, smoke-tests, rolls back on failure (JUDGE_AUTO_UPDATE=0 skips; skips while 8765 is served)
.venv\Scripts\python -m pytest                               :: offline suite, no judge tokens (what CI runs)
.venv\Scripts\python -m pytest -m smoke                      :: fast wiring checks
.venv\Scripts\python -m pytest tests/test_app.py::test_name  :: single test
node --test tests/js/report.test.js                          :: PDF report JS tests (also run by pytest via tests/test_report_js.py; skipped without Node)
```

Live metrics against the real judge (spends tokens): `set RUN_LIVE_JUDGE=1`, then `.venv\Scripts\python -m pytest -m live`.

- Config comes from `.env` (see `.env.example`): `JUDGE_API_KEY` (required), `JUDGE_MODEL`, `JUDGE_BASE_URL`, `JUDGE_DB_PATH`, `JUDGE_LOG_LEVEL`, `JUDGE_MAX_BODY_MB`, `JUDGE_CONCURRENCY`, `JUDGE_METRIC_CONCURRENCY`, `JUDGE_TARGET_TIMEOUT_S` (seconds per chatbot reply, default 60, 5-900: `http_client.target_timeout`), `JUDGE_AUTO_BUILD`, `JUDGE_BUILD_MAX_MESSAGES`, `JUDGE_BUILD_MAX_JUDGE_CALLS`.
- `pytest.ini` disables the globally installed deepeval/opik/langsmith pytest plugins; keep that.
- No linter/formatter is configured. CI (`.github/workflows/ci.yml`) runs the offline suite on Python 3.13; the live job is manual-dispatch only.
- The web app has no build step: start the backend and open `http://127.0.0.1:8765/` (or run `start-llm-judge.bat`; see `ChatbotExtension/README.md`). Hard-refresh (Ctrl+Shift+R) after editing its files. There is no Chrome extension any more (the folder keeps its old name).

## Keeping the docs current

A change that adds or alters behaviour updates its docs in the same change:

- `docs/WORKFLOW.md` (text) and `docs/workflow.html` (diagrams): the sections the change touches, any counts they quote (metrics, routes) and the footer date in `workflow.html`.
- Then republish `docs/workflow.html` to its fixed link, https://claude.ai/artifact/JxkuyFH5iLH8ZdzoszZ4Qv (linked from `README.md` and `docs/WORKFLOW.md`): Artifact tool `action: "read"` on that URL, then publish `docs/workflow.html` with `url` set to it. A publish without `url` creates a new link and leaves the shared one stale.
- This file for architecture facts, and `README.md`, `docs/ADVANCED_TOOLS.md` or `ChatbotExtension/README.md` where they describe what changed.

`.claude/hooks/docs_guard.py`, a Stop hook in `.claude/settings.json`, enforces it: it blocks finishing a turn once when backend code, web-app files, start scripts, `*.default.json` datasets, `requirements.txt` or CI files are newer than both workflow docs. When a change needs no doc update, run `python .claude/hooks/docs_guard.py --ack` (touches the git-ignored `.claude/docs-reviewed`).

## Architecture

- **`backend/dashboard/app.py`** — the whole HTTP API. At import it opens SQLite (`storage.init_db`, which also migrates legacy target configs). No CORS middleware (the web app is same-origin, so every other origin is refused) and `TrustedHostMiddleware` only `127.0.0.1`/`localhost` — deliberate (protects stored target API keys); don't add CORS for `*`.
- **`backend/metrics_catalog.py`** — single source of truth for metrics. Each `MetricSpec` bundles the DeepEval metric builder, how to build an `LLMTestCase` from a golden row + reply, the dataset (`goldens` or `goldens_with_context`), and `needs` (reference data required for ad-hoc judging). 90 specs in 8 groups (58 + 32 DeepTeam vulnerability specs, `DEEPTEAM_SPECS`; the 58 include `EXTRA_DEEPEVAL_SPECS` (MCP Use, Multi-turn MCP Use, MCP Task Completion: MCP targets only (`features['mcp']`, from `McpTargetClient.mcp_server()` via `runner._with_mcp` / `app._runtime_config` `_mcp`), tool results as `mcp.types.CallToolResult` (the `mcp` SDK is in requirements.txt); Misuse, Non-Advice (DeepEval), Role Violation (DeepEval), Topic Adherence, Goal Accuracy, Tool Use, Tool Permission, Agent Loop Detection, Pattern Match, JSON Correctness: DeepEval's own classes, configured by `text` settings (`_text_setting`, rendered as text inputs on the Advanced tools page) and RAGAS, DeepEval's `RagasMetric` run on the judge by `backend/judges/ragas_adapter.py` (`JudgeChatModel` LangChain adapter + `LocalEmbeddings`, which share one embedder loaded under a lock by `_shared_embedder`; `build_ragas_metric` first calls `_warm_imports`, which imports transformers / sentence_transformers / datasets / ragas once under that lock, because datasets checks `transformers.PreTrainedTokenizerBase` whenever transformers is in sys.modules and a case thread seeing it half-imported raised "no attribute 'PreTrainedTokenizerBase'"), unavailable until the optional `ragas instructor "datasets<5"` packages are installed (datasets 5 pulls huggingface_hub 2, breaking transformers / DeepEval's click pin; it averages only the sub-scores ragas returned, NaN parts named in the reason, all NaN = case error) (not in requirements.txt: instructor caps jiter<0.15, forcing an older openai), `opt_in` so unticked by default, `combines` lists its 5 sub-scores) plus "custom" (`GROUPS`; "agent" and "reference" hold the agent metrics and the no-judge text-match scorers in `backend/text_match.py`: Exact Match, ROUGE-L and BLEU-1 call DeepEval's `Scorer` (needs `rouge-score`, `nltk` + `punkt_tab` data fetched on first use)); each has `direction` ("higher"/"lower"), a default `threshold`, `presets()` per environment (`ENVIRONMENTS`), and `kind` ("single"/"conversation"). Scores are DeepEval's own: hallucination, bias, toxicity and pii_leakage are "higher" too (DeepEval 4 scores them 1 = clean; `storage._migrate_deepeval_scale` moved old runs once, `ui.js` moves saved thresholds once). "lower" remains only for user-made violation-rate metrics, via `deepeval_threshold`/`reported_score`. A job sends each question once: `targets/shared.SharedReplies` (per job in `app._job_clients`) gives every metric the same reply, as DeepEval scores one test case with many metrics; `multi_sample` and `attack` specs use `.fresh`. Jobs may carry `deepeval` {strict_mode, include_reason, async_mode} (`metrics_catalog.apply_deepeval_options`; strict sets threshold 1). Judge consistency, the latency limit and `check_replies` are opt-in extras, not DeepEval. `/api/run` and `/api/judge` take the per-metric `threshold` the side panel stores in `localStorage` (`llmJudge:thresholds` {key: value}, `thresholdEnv`). As in DeepEval, each case passes on `metric.is_successful()` and a run passes only when every case passes (`cases_passed`, `pass_rate` in the result; the average is shown, not gated). Metrics a job cannot run (not applicable, or no case in the golden set) are kept as `options.skipped` [{key, title, reason}] (`app._skip_reason`, also `skip_reason` in `/api/metrics`) and shown by scans and the report. Conversation scenarios: shipped in `conversations.default.json`, edited copy `conversations.json` (gitignored, reset with the goldens on every panel load, CRUD at `/api/conversations`). Security probes (9 red-team G-Eval metrics incl. `harmful_content`, group `security`): shipped in `security_probes.default.json`, edited copy `security_probes.json` (gitignored, reset together with the goldens, CRUD at `/api/security-probes`); a target's optional `persona` goes into each probe's context, and its `probe_set` (`generic` default, or `ecommerce`) picks which probes are sent. The same store holds adversarial prompts for `bias`, `toxicity` (dataset `safety_probes`: probes first, then the goldens) and `no_prompt_leak` (dataset `prompt_leak_probes`: probes only); `security_probes.PROBE_METRICS` lists every metric a probe may name. DeepTeam (see the DeepTeam bullet) adds one security G-Eval per vulnerability the app had no metric for (keys from `deepteam_sync.metric_key`: snake case, `dt_` for clashes such as `dt_hallucination`; Bias / Toxicity / PII Leakage / Prompt Leakage map to bias / toxicity / data_exfiltration / no_prompt_leak); their probes (DeepTeam template examples, up to 10 per metric, ids `sp_dt_`) are added to the `generic` set by every seed/reset (`security_probes._defaults`; tests replace `deepteam_defaults` with `[]`), and a probe set without its own uses them. `/api/metrics` rows carry `source` ("deepteam" / "app"), `optional_on` (fields read only when present) and, for DeepTeam specs, `deepteam_metric` / `deepteam_fields` (`metrics_catalog.DEEPTEAM_METRIC_CLASSES` / `DEEPTEAM_AGENT_FIELDS`, verified against the installed package by `tests/test_metric_required_params.py`; the side panel's metric hover card shows them); the side panel and the dashboard (`dashboard.js isTicked`: its totals and Run all visible) treat DeepTeam metrics and `opt_in` specs (RAGAS) as unticked when no `checkedMetrics` is saved. Every spec also carries dashboard card copy (`ui_category`, `scale_hint`, `question`), and `/api/metrics?target_id=` adds `cases_available`; `GET /api/metrics/{key}/cases?target_id=` lists the cases a run sends and `POST` adds one to the store that metric reads (`app._case_add_kind`: golden in the chatbot's theme, probe in its probe set, or conversation scenario) and `DELETE .../cases/{case_id}` removes one (a golden from the whole set; a built `auto_` scenario by saving the others), behind the side panel's per-metric "Test cases" / "Add" buttons and each case's Delete; specs that score `retrieval_context` use only the chatbot's own sources (target `context_path`, or `sources_fallback` passages for non-retriever specs): production evaluation, never the golden's context (`metrics_catalog` sets `needs_own_sources` on every such spec, so without sources they are `unavailable`; a reply with none is a not-applicable case, `runner.NO_OWN_SOURCES_CASE`; Turn RAG specs ignore a scenario's `context`). Hallucination still reads the golden's `context` (known facts, as in DeepEval). Each spec's `scores_on` / `criteria` feed the dashboard; every shipped G-Eval spec also has fixed `evaluation_steps` (passed to DeepEval's `GEval` via `_geval`, security probes via `_security_steps`; `/api/metrics` lists them; calibration examples become one extra step), so the judge never writes steps itself; result rows carry `input`, `actual_output`, `expected_output`, `context`, `context_source`, `score`, `passed`, `reason`. Both the API and the tests import from here. Run-time applicability (see docs/WORKFLOW.md "Metrics that switch on at run time"): `MetricSpec.applies(features, items)` (features = target has `context_path` / `tools_path`) makes a metric `unavailable` in `/api/metrics` and an error run that sends nothing; `skip_before` / `skip_case` / `not_applicable` leave single cases out (`runner._NotApplicable`, result `cases_not_applicable`). Turn RAG metrics read each turn's `retrieval_context` (kept by `runner._run_conversation`) or a scenario's optional `context`; Prompt Alignment's `instructions` come from `targets/instructions.resolve` (via `metric_options`): typed on the chatbot, else the captured request's system prompt, else standard production rules (`BASE_RULES` + `RAG_RULES` / `AGENT_RULES` / a role rule when the chatbot has `context_path` / `tools_path` / `persona`); the run's `note` names the source, and the exact rules are saved with the run as `result.prompt_instructions` {source, source_label, rules} (`instructions.describe` / `SOURCE_LABELS`), shown by `ui.js promptInstructionsBlock` on the scan page, in the report, in the side panel's Test cases panel and hover card (from `/api/metrics` row `prompt_instructions` for the chosen chatbot). A target's optional `sources_fallback` (`knowledge_base`: BM25 over the theme's uploaded documents; `cited_links`: public pages the reply links to; `backend/rag/derived_sources.py`) supplies `retrieval_context` when the response has none, for every spec except `grades_retriever` ones (Contextual Precision / Recall / Relevancy and their Turn versions); rows get `context_source` `knowledge_base` / `cited_pages` (docs/WORKFLOW.md "Sources the app finds itself"). Agent metrics read `ChatReply.tools_called` (target `tools_path`, parsed by `curl.tool_calls`) and goldens' optional `expected_tools`. Auto-discovery (docs/WORKFLOW.md "Paths found during scans"): `HttpTargetClient.discovered` collects tool / source paths seen in replies (JSON or stream) that the target has none saved for; `app._save_found_paths` saves them (never over a typed path) and `app._after_job` (the `JobQueue` `after_job` hook) stores them in `jobs.discovered` and queues one follow-up job of the metrics they switched on (`app._availability`, same check as `/api/metrics`), options (minus that job's `skipped` and `confident`) + `auto_discovered`; scans get a `note`. Pairwise jobs are not watched.
- **`backend/dashboard/runner.py`** — `run_spec` sweeps a theme's goldens against a target and stores **one** aggregated row per run (charts plot run averages); `limit` (the dashboard's cases per run) caps the cases scored: cases a metric leaves out (`_NotApplicable`: no tool called, no context found, no plan) are backfilled with the next goldens, batch by batch, until `limit` are scored or the set runs out and `persona` feeds the security probes; cases run on `case_workers` threads (`JUDGE_CONCURRENCY`, default 4, also the judge's cap on calls in flight; conversations, attacks and targets with `send_delay` stay serial), each thread with its own metric instance, rows kept in case order; `_case_slots` caps cases in flight across all runs at `JUDGE_CONCURRENCY` (tests pin it and `jobs.METRIC_CONCURRENCY` to 1 via the `serial_cases` fixture); `judge_one` scores a single ad-hoc answer and persists nothing. Each run also records how it was judged (`judge_model`, `judge_tokens`, `judge_calls`, `target_calls`, `duration_s`, `judge_spread`: columns added by `storage.RUN_EXTRA_COLUMNS`, counted by the run's own `usage.meter()`, a contextvar that worker threads get through `contextvars.copy_context()`, so runs side by side don't mix) and notes a judge model change since the previous run; `check_consistency` (`/api/run`, side-panel setting `checkConsistency`) scores every reply twice and averages; when the two differ by more than `UNSTABLE_SPREAD` (0.15) it scores a third time and keeps the median (the run's `note` counts these tie-breaks), and flags `judge_unstable` when, even then, no two of a case's scorings agree within 0.15. Failures come back as `status: "error"` dicts, not exceptions. Runs from the web app go through `backend/dashboard/jobs.py`: `POST /api/jobs` queues a batch (one job at a time on a worker thread, reusing `run_spec`; up to `JUDGE_METRIC_CONCURRENCY` (default 2) of its metrics run side by side (a job's `metric_concurrency` option, 1–8, overrides it: the web app's "Parallel metrics" select, bounds from `GET /api/run-limits`; "Run mode" is the saved `casesPerRun` sent as `limit`), pairwise jobs one at a time; `current` is the first running metric, `running` lists all), `GET /api/jobs/{id}` reports progress and results, unfinished jobs become `interrupted` on start, the web app's Stop calls `POST /api/jobs/cancel-all` (every queued/running job of every chatbot; `backend/cancel.py` contextvar check makes `HttpTargetClient.send` and `GroqJudge._call` raise `RunCancelled` before their next call, and a stopped job queues no auto-discovered follow-up), and each run's full result is stored in `runs.result_json` (returned as `result` by `/api/runs/latest`). Tests set `JUDGE_START_JOB_WORKER=0` and call `jobs.process_next()` themselves.
- **`backend/targets/`** — one connector, `HttpTargetClient` (type `http`): replays a request captured from the chatbot's website. `presets.py` builds that same config for an OpenAI-compatible LLM (`POST /api/targets/parse-llm` → url/headers/`messages` body, reply at `choices.0.message.content`), so `pytest -m live` can judge another model without a capture; the side panel's "Or fill from an LLM API" fills the chatbot form with it. Config is `{url, method, headers, body_template, response_path, theme}`; `{{message}}` marks where the question goes (JSON-escaped in bodies, URL-encoded for form bodies/URLs). Replies come from a JSON path, from SSE `data:` events joined at that path, or as raw text when the path is empty. `curl.py` turns "Copy as cURL (bash)" into that config (`/api/targets/parse-curl`); it now also treats an `id` / `ticket` / `ticketid` / `query` parameter as the message for ticket-lookup APIs (MetTel Compass, Jira, etc.). `/api/targets/test` tries an unsaved config. Header values (cookies, keys) are masked as `***` in responses, and a PUT without `headers` keeps the stored ones; a PUT that leaves `tools_path` / `context_path` empty keeps a path a scan found. Optional `max_message_length` (longer messages raise `MessageTooLong`; the runner skips those cases and passes `max_chars` so Summarization cuts its source to fit), `send_delay` (seconds between messages, enforced per chatbot URL across clients and threads via `_PACES`), and `check_replies` (default false, opt-in: `reply_check.service_message` turns replies like "limit reached" / "please log in" / empty into `ChatbotUnavailable`, a run error that records nothing). 408, 429, every 5xx (a chatbot often wraps its LLM provider's 429 in a 502), timeouts and refused connections are retried 3 times (`_retryable`, `ChatbotUnreachable`; Retry-After else 2/4/8 s; Stop checked before each try); other 4xx are not, and 401/403 say to refresh the cURL. `tests/conftest.py` `no_retry_waits` makes the waits instant (send_delay tests keep real time). The canned-answer chatbot used by tests lives in `tests/fakes.py`, not in the product.
- **MCP targets and Build all test data** — type `mcp` (`TARGET_TYPES`): `backend/targets/mcp_client.py` `McpTargetClient` (stdio subprocess with a minimal env + config `env`, or streamable HTTP; JSON-RPC handshake once, per-call timeouts, Stop checks, 5 MB cap, process tree killed on close); the agent model (`agent_model` on the judge's provider, else the judge, with a run note "The judge model also chose the MCP server's tools" added by `app._spec_for_target`) picks a tool per message; replies always report tools, so MCP targets count as having tools. `storage._migrate_targets` keeps `mcp` rows. Env / header values masked `***` (a `***` value or missing field keeps the stored one). `POST /api/targets/mcp/tools` `{config, target_id?}` -> `{tools, server}`. `/discover` and the CI export refuse MCP targets. Build all (automatic, gap-driven): `POST`/`GET /api/targets/{id}/prepare-all` (`generate: true` required; 503 without a judge) runs `backend/datasets/prepare_all.py` `build_testdata` in the background under `cancel.watching` (`POST .../prepare-all/cancel`, the panel's Stop `#testdata-stop`, ends it at the next message / judge call: status `stopped`; paths found in replies are set on the client within the same build; a form save keeps `app.BUILD_KEYS`), steps profile / goldens / scenarios / context / tools / probes (`STEPS`), each filling only the gap to its minimum (5 goldens of which 3 short "fact" ones, 3 scenarios, 3 Context goldens, 2 `expected_tools` goldens per tool, fitted probes per metric); `profile.py` interviews once, sets `config.profile` (`kind` chat/rag/agent/mcp, `tools_seen`, `tool_reasoning_seen`) and writes a persona only when none is typed; goldens are checked against help pages / documents / instructions (else `auto_unverified` with `status: "draft"`, which runs skip until reviewed on the Advanced tools page); the context step never invents passages: with no source it is skipped (`prepare_all.NO_CONTEXT_SOURCE`), tool goldens are kept only when the chatbot calls a tool, rag/agent scenarios without returned sources get passages; `build_kit.py` `Budget` caps a build at `JUDGE_BUILD_MAX_MESSAGES` (30) chatbot messages and `JUDGE_BUILD_MAX_JUDGE_CALLS` (40) judge calls, then skips the remaining steps with `BUDGET_MESSAGE`; probes go to the chatbot's own set `target_<id>` (`security_probes.target_<id>.json`, git-ignored, survives reset, deleted with the chatbot) and the build switches its `probe_set` to it; the status lists `metrics: {ready, missing}`, `kind` and `leftovers` (`app._leftovers`: missing metrics with `LEFTOVER_HINTS`, Plan Quality / Plan Adherence when tools carry no reasoning, and metrics that do not apply to the kind with reason "Does not apply to this target"). `GET /api/build/settings` returns `{auto_build}` (`JUDGE_AUTO_BUILD=0` off): the panel starts the build by itself after saving a chatbot, and once for a never-built (`config.auto_built`) chatbot with hinted leftovers. Side panel: Add a chatbot switch (Website chatbot / MCP server), MCP form with Test & list tools, live build progress with the kind line (`#testdata-kind`) and leftovers list (`#testdata-leftovers`), the post-save question only when auto build is off, **Build all test data** button; `prepareGoldens` now always sends `generate: false` (tests/js/sidebar_mcp.test.js).
- **`backend/judges/judge.py`** — wraps the judge as a DeepEval `LocalModel` with rate-limit retries. Optional judge result cache (`backend/judges/cache.py`, enabled with run option `cache_judge_results`) reuses identical evaluations (same test case + metric criteria) to save tokens. The judge must never be the chatbot under test.
- **`backend/traffic.py`** — console traffic log (`llm_judge.traffic`, on unless `JUDGE_LOG_TRAFFIC=0`): `HttpTargetClient.chat` logs each question/reply, `GroqJudge`'s wrapped `create` logs each judge call (prompt size, time, tokens, output) and sets a 90 s per-read timeout (`JUDGE_TIMEOUT_S`; without it a hung call stalled runs ~30 min) plus a 150 s wall-clock cap (`judge._with_deadline`, `JUDGE_DEADLINE_S`: providers that trickle keep-alive bytes never trip the read timeout; one call hung 39 min) after which `GroqJudge._call` retries it up to twice, and Stop ends the wait at once, `jobs.py` logs metric start/finish. Text is clipped to 300 chars; headers/keys never logged. `hardening.configure_logging` also writes the `llm_judge` logs to `logs/traffic-YYYY-MM-DD.log` (`JUDGE_TRAFFIC_FILE`, empty = off; tests set it empty), which `watch-traffic.bat` tails, however the backend was started.
- **`backend/usage.py`** — in-memory judge token / call counter (`GroqJudge.load_model` wraps the OpenAI client once; `HttpTargetClient.send` counts chatbot calls), served at `/api/usage` and reset with the process or `POST /api/usage/reset`.
- **Goldens** — `backend/datasets/goldens.json`, grouped by theme (`generic` default: bot-agnostic; behaviour-style answers plus goldens with context; `metrics_catalog.ask` always sends the question alone (a golden's old `context_in_prompt` flag is ignored); `general_support` is the ShopEasy shop set), edited through the API/side panel. `goldens.json` is runtime state: like `conversations.json` and `security_probes.json` it is seeded from `goldens.default.json` on first use (`goldens._read_all`) and git-ignored. Edits are session-only for shipped themes: the side panel calls `POST /api/goldens/reset` on every load, which restores the themes in `goldens.default.json` (the defaults to edit) and keeps other themes. Every write goes through `_write_all`, which appends what changed and the calling function to `goldens_changes.log` next to the file (gitignored); `shipped_health()` / `GET /api/goldens/health` counts missing shipped rows, which the side panel reports. The autouse fixture in `tests/conftest.py` redirects `GOLDENS_PATH` to a copy of `tests/data/goldens.json` for every non-smoke test.
- **Document → goldens (`backend/rag/`)** — `POST /api/documents/url {theme, url}` fetches a help page (`fetch.py`: http(s) only, 5 MB cap, stdlib HTML-to-text, refuses pages under 200 chars) and feeds its text through the same generator. `POST /api/documents` saves the upload under `backend/datasets/documents/<theme>/`, runs the DeepEval `Synthesizer` (judge as critic, local sentence-transformers embedder in `embeddings.py`), and appends goldens. `app.py` imports this lazily inside a wrapper named `generate_goldens_from_document` because `sentence_transformers` takes ~40s to import. Keep it out of module-level imports and keep the wrapper name: tests patch `app_module.generate_goldens_from_document` and `backend.rag.embeddings.SentenceTransformer`. A new chatbot's dataset is built by `POST /api/targets/{id}/prepare-goldens` (side panel, after the user says yes with `generate: true`): own theme + starter goldens, then `backend/datasets/autogen.py` interviews the chatbot (`INTERVIEW`), searches its site for FAQ / help / docs pages when no `help_url` is given (`find_help_pages`: Origin/Referer, the chatbot host and its main domain × `HELP_PATHS`, max 12 fetches; sets `docs_searched` and `help_url`), queues found pages through the document pipeline, and has the judge write goldens (`source: "auto_chatbot"`) and conversation scenarios fitted to it (`write_dataset`). Each step runs once per chatbot.
- **Storage** — `backend/storage.py`, SQLite tables for targets, runs, documents, jobs, `pairwise_runs` and `human_labels` (busy timeout 10 s). New run columns go in `RUN_EXTRA_COLUMNS` (nullable, additive): `latency_p50`, `latency_p95`, `judge_cost_usd` were added that way. Fresh sessions: each panel load calls `POST /api/session/start` (returns the max run id) and stores it as setting `freshSinceRunId`; scores, trend, cases and the report pass it as `since_id` (the report and the dashboard's Details read cases only from `runs.result_json`, no browser copy) to `/api/runs/latest` / `/api/history`, so they start empty while every run stays stored; the opt-in **Show earlier runs** checkbox (dashboard header, report options; setting `showAllRuns`, `ui.js showingAllRuns()` / `setShowAllRuns(on)`, which also sets `runsChangedAt` so open panes reload) makes `sessionSince()` return 0. The dashboard's History view lists scans (see Scans) rather than single runs, and deletes them all at once (`DELETE /api/targets/{id}/runs`, runs and finished jobs; `DELETE /api/runs/{id}` still removes one run) or one at a time (each row's Delete, `DELETE /api/scans/{job_id}`, disabled while the scan is queued or running); deletes, and every scan as it ends (`ui.js followJob`), broadcast setting `runsChangedAt` so open views reload.
- **Roadmap features (Advanced tools page, `ChatbotExtension/advanced/`)** — all additive; runs without the new options behave as before. `MetricSpec` gained `settings` (tunable knobs passed to `build_metric` via `metrics_catalog.metric_options`), `needs_target` (target config fields, e.g. Prompt Alignment's `instructions`; a run without them is an error), `runner_settings` (knobs the runner reads instead) and `variants` (kind `multi_sample`: Robustness / Self-Check send several messages per golden). Spec kinds: `single`, `conversation`, `attack` (Multi-turn Jailbreak: `runner._run_attack`, the judge writes each escalating turn), `multi_sample`.
