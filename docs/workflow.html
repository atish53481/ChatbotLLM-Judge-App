LLM Judge · how it works

From a pasted cURL to a scored scan

LLM Judge replays a request captured from a chatbot's own website, asks it the questions in a golden set, and has a separate judge model score every reply with DeepEval metrics. This page follows that path through the code, from the start script to the scan you read afterwards.

The pieces

Everything runs on your PC except the chatbot and the judge

The app has two halves: a web app with no build step (ChatbotExtension/, named from when it was a Chrome extension) and a FastAPI backend that serves it and does all the work. A run never happens in the browser. The page queues a job, and a worker thread inside the backend sends the questions and collects the scores, so closing the page does not stop it.

Panes stay in step
The side panel, dashboard and result pages share settings through localStorage (llmJudge:*) and the browser's storage event: the chatbot picked, thresholds, Run mode, the last run.
The judge is its own model
It must never be the chatbot under test. GroqJudge wraps it as a DeepEval model: at most 4 calls in flight (JUDGE_CONCURRENCY), 90 s per read and 150 s wall clock per call (JUDGE_DEADLINE_S: a hung call is abandoned and retried up to twice, and Stop ends the wait at once), retries on rate limits, every token counted.
The chatbot is called like its own site calls it
The client replays the captured request with the question in place of {{message}}, waits up to JUDGE_TARGET_TIMEOUT_S seconds for each reply (default 60), retries HTTP 408, 429 and 5xx replies, timeouts and refused connections three times, keeps the chatbot's Delay between messages, and reads the reply from a JSON path, a stream of data: events, or the raw text.
What starts with the backend
On import it opens judge.db (migrations; jobs left unfinished become interrupted), starts the job worker thread, and refreshes the daily red-team probes in the background when the last refresh is over 24 hours old.

Your path

From double-click to the first scores, in eight steps

  1. 1

    Start the app

    Double-click start-llm-judge.bat. If a backend already answers on port 8765, it only opens the browser. Otherwise run-backend.bat builds .venv on the first run, stops an older LLM Judge backend still holding the port, runs update-packages.bat (upgrade, including deepteam; smoke tests; roll back if they fail) and starts uvicorn. When the installed deepteam is newer than the saved catalog, the backend reads it again the first time it loads the DeepTeam catalog, before building any metric (deepteam_sync.load_catalog, a few seconds, no judge call), so new vulnerabilities and their test cases arrive with that start. The browser opens once /app/ answers, and everything the backend prints also goes to logs\llm-judge-YYYY-MM-DD.log.

    • GET / → /app/
    • uvicorn backend.dashboard.app:app
  2. 2

    The page loads automatic

    The side panel and the dashboard open side by side. The panel puts the shipped golden answers, scenarios and probes back, and starts a fresh session so scores begin empty while older runs stay under History (tick Show earlier runs on the dashboard or the report to count them again). Then it loads the judge settings, the metric catalog and your chatbots.

    • POST /api/goldens/reset
    • POST /api/session/start
    • GET /api/status
    • GET /api/metrics
    • GET /api/targets
  3. 3

    Connect a judge

    In Judge settings, pick a provider (Groq, Command Code, OpenAI, NVIDIA or any OpenAI-compatible API), paste its key and model, press Test, then Save. A JUDGE_API_KEY in .env works too. Without a judge, runs are refused with HTTP 503.

    • POST /api/judge/settings/test
    • PUT /api/judge/settings
  4. 4

    Add the chatbot

    On the chatbot's website, open DevTools → Network, send it a message and copy that request as cURL (bash). Pasted into Add a chatbot, the app finds the message you sent, puts {{message}} in its place, sends the request once and finds where the reply is, plus any tool calls or sources. To judge a model instead, fill the form from its OpenAI-compatible API. Test, then Save chatbot.

    • POST /api/targets/parse-curl
    • POST /api/targets/parse-llm
    • POST /api/targets/test
    • POST /api/targets
  5. 5

    Build its test data

    A new chatbot gets a golden set of its own, and its test data is built automatically right after you save it (JUDGE_AUTO_BUILD=0 turns that off and the panel asks first). Six steps, each filling only the gap: profile (the app asks the chatbot what it is, which tools it calls and whether it returns sources, and sets its kind: chat, RAG, agent or MCP), goldens (until it has 5, 3 of them short answers; checked against its help pages and documents when there are any), scenarios (until 3, with role, expected outcome and source passages filled in), context (Context goldens from its FAQ pages), tools (tool tests for Tool Correctness, kept only when the chatbot really calls a tool) and probes (security probes fitted to it). A build sends at most 30 messages and makes at most 40 judge calls (JUDGE_BUILD_MAX_MESSAGES, JUDGE_BUILD_MAX_JUDGE_CALLS); past that it stops with “Build budget reached” and keeps what it wrote. Stop ends a running build before its next message or judge call (POST /api/targets/{id}/prepare-all/cancel, status “stopped”), keeping what it wrote. A tool-calls or sources path a reply shows is used at once, in the same build. It then lists the metrics still without test cases, each with why and what to do, and a separate “Does not apply” group for metrics that do not fit this kind of chatbot. Build all test data runs it again and fills only what is missing. Answer no to type your own.

    • POST /api/targets/{id}/prepare-all
    • GET /api/targets/{id}/prepare-all
    • POST /api/targets/{id}/prepare-all/cancel
    • POST /api/documents
    • POST /api/documents/url
    • POST /api/goldens
  6. 6

    Fill in what metrics need optional

    Some metrics need the bot's rules, tool calls or retrieved sources, which a cURL may not show. Find missing metric data, after you confirm you may test the bot, reads its OpenAPI docs, tries the request with a debug flag, reads its help pages and asks up to 10 of its own questions, with at most 20 fetches in all. You can also give it the docs yourself: an OpenAPI / Swagger link or file, and help, FAQ or log text or a file. Nothing is used until you tick what it found and apply it; the rest is scored black box.

    • POST /api/targets/{id}/discovery/extract
    • POST /api/targets/{id}/discover
    • POST /api/targets/{id}/discovery/apply
  7. 7

    Run the judge

    First pick the Framework to scan with: DeepEval (quality, retrieval, agent, conversational, G-Eval, safety, text match, custom), DeepTeam (red-team attacks and DeepTeam vulnerabilities) or Both. The list shows that framework's groups, and Run judge and the quick-select buttons use only its metrics. Tick metrics under Metrics to run. Each has a threshold, and Thresholds for applies a preset for Local Development, PR, Staging or Production. Pick Run mode (1, 2, 3, 5 or all cases per metric) and Parallel metrics, then press Run judge, or Run all visible on the dashboard. The scan keeps running if you close the page; Stop ends every queued and running scan. Hover a metric's name to see its category, single- or multi-turn, and which DeepEval test-case fields it needs (Input, Expected output, Context, Retrieval context, Turns, Tools…).

    • POST /api/jobs
    • GET /api/jobs/{id} every 1 s
    • POST /api/jobs/cancel-all
  8. 8

    Read the results

    The side panel shows Latest scores, and a browser notification says when the scan ends. The dashboard has a card per metric, the score trend and the last run case by case. History lists every scan and opens the scan page, the test-run pages (Overview, Test Cases, Compare, Eval Insights), the Risk Assessment, Regressions and the PDF report, and sends a scan to Confident AI.

    • GET /api/runs/latest
    • GET /api/targets/{id}/scans
    • GET /api/scans/{id}
    • GET /api/scans/{id}/insights

Test data

Every metric reads one dataset

A test case is a question, a multi-turn scenario or a red-team probe, plus whatever the metric needs to score the reply: an expected answer, context facts, expected tools. The cases live in three JSON files next to the code, and each chatbot points at a theme, its own golden set. In the side panel, Test cases on a metric lists exactly what a run will send, and Add puts a new case in the store that metric reads.

Drafts wait for review
Goldens generated with review on are saved as drafts. Runs skip them until you accept them (POST /api/goldens/review).
Probe sets per chatbot
A chatbot's Security probes setting picks generic, e-commerce or latest. Latest is rewritten daily from OWASP pages and the installed DeepTeam's own vulnerability text, 10 probes per metric, and falls back to the shipped set when offline. The daily refresh covers the app's 13 probe metrics plus the DeepTeam metrics some chatbot ran in the last 30 days (13 judge calls a day on a fresh install; JUDGE_PROBE_REFRESH_ALL=1 for all 45).
DeepTeam test cases
Every panel load adds up to 10 cases per DeepTeam metric to the generic set: DeepTeam's template examples, spread over the vulnerability's subtypes and labelled with the DeepTeam version. A set with none of its own (e-commerce) uses them too. An example that is only a payload (a bare URL or command) is worded as a request first, so the chatbot gets a message, not just a link.
Every golden edit is logged
Writes to goldens.json append what changed, and the function that changed it, to goldens_changes.log.

A scan

One click queues one job, and the backend runs it to the end

A scan is a job: the metrics you ticked, for one chatbot, with the options set at that moment. Jobs run one at a time in the order they were queued, so a second scan waits behind the first. Inside a job, Parallel metrics decides how many metrics run at once (1 to 8, default 2).

Progress
GET /api/jobs/{id} returns the results so far and, per running metric, its phase (chat or judge), cases done of total and the question being asked. Pages poll it every second, and a reopened page finds a running job again (/api/jobs?active=1).
Stop
POST /api/jobs/cancel-all stops every job of every chatbot. Queued jobs end at once. A running one stops at its next chatbot message, judge call or retry wait (backend/cancel.py); a judge call already in flight is not waited for. A stopped metric records nothing, so a half run never skews the trend.
Errors stay inside the result
A broken dataset, an empty one or a chatbot failure comes back as that metric's status: "error" with a message. Only a missing judge or a deleted chatbot ends the whole job.

One metric

Inside a run: five stages, with a loop per case

runner.run_spec runs one metric for one chatbot. Run mode sets N, the number of cases to score. Cases a metric cannot use are left out and replaced by the next ones in the reserve, so N means N scored cases wherever the set has that many.

Single question · 33 metrics
The golden's question, or the prompt the metric builds from it: Summarization sends the text to summarize, and grounded goldens send their facts with the question.
Conversation · 8
Each user turn of a scenario in order, with the conversation so far in the body's history slot. Turn RAG metrics read each turn's own sources.
Several samples · 2
Robustness sends the question with a typo and as a casual rewording; Self-Check asks the same question several times. Always fresh replies.
Attack · 1
Multi-turn Jailbreak: the judge writes each escalating user turn (4 by default) and the rubric scores the whole transcript.
Where context comes from
The chatbot's own sources (Retrieved context path) win. Without them, a chatbot can have the app find some: passages from its uploaded documents (BM25, top 3) or up to 3 public pages its reply links to. The golden's context is never used in their place: without sources, those cases are not applicable. Each row's context_source says which was used.
What a run records
One runs row: average score, passed, cases run, judge model, tokens and calls, chatbot calls, duration, latency p50 / p95, judge cost. Its result_json holds every case row (input, actual output, expected output, context, score, passed, reason, latency) and notes such as a judge model change since the last run.

Shared replies

Each question is sent once per scan

In DeepEval, a test case is one reply that many metrics score. A scan works the same way: the job's metrics share one chatbot client, so the reply that Answer Relevancy scored for a question is the same reply Correctness scored.

Pass and fail

A run passes only when every case passes

The app follows DeepEval's rules rather than averaging. The average score is shown on every card and chart, but it never decides a result.

Example numbers. Faithfulness averages 0.84, above its 0.8 threshold, and still fails because Q2 scored 0.71. The scan reads “2 of 3 test cases passed · 2 of 3 metrics passed”.

  • CasePasses when DeepEval's is_successful() says so: the score meets that metric's threshold. Strict mode raises the threshold to 1.
  • Metric runPasses only when every case passes. A latency limit (Advanced tools) can fail it too, when 95% of replies take longer than the limit.
  • Test casePasses only when every metric that scored it passes it.
  • ScanPassed when every metric passed, failed when at least one failed, incomplete when a metric errored, nothing was scored or the scan was stopped.

Results

Two records feed every view

Every finished metric run is a row in runs; every scan is a row in jobs. The quick views read runs and start empty on each panel load, since they pass since_id, the session start. History reads scans and keeps everything until you delete it. When a scan ends or anything is deleted, every open page reloads these views.

Side paths

Tools that work outside a scan

Chat
POST /api/chat talks to the chatbot from the dashboard, sending the last 40 turns. Nothing is scored.
Judge this answer
POST /api/judge scores one reply on the spot (judge_one) and stores nothing. Metrics that need an expected answer or context take it from the matching golden, or say what is missing.
A/B test
POST /api/pairwise queues a pairwise job in the same queue: the judge compares two chatbots on each golden, in both orders.
Simulate
POST /api/simulate has the judge play the user for a few turns, scores the talk with conversational metrics, and can save it as a scenario.
Calibrate
POST /api/calibration stores your own score for a case of a stored run. With calibration on, these labels join the G-Eval criteria as examples.
Export
GET /api/export/suite returns a zip of a chatbot's test suite for CI. Header values such as keys and cookies are never exported. Security metrics go in with the probes this chatbot's probe set sends (probes.json, run by test_red_team), and Bias and Toxicity send their adversarial probes before the goldens, as in the app; the multi-turn attack and attack enhancers stay in the app.

Metrics

76 metrics in eight groups, plus your own

Each metric is one MetricSpec in backend/metrics_catalog.py: the DeepEval metric it builds, the dataset it reads, what it needs, a default threshold and a preset per environment. Bias, for example, needs 0.4 locally, 0.6 on a PR, 0.7 in staging and 0.8 in production. Every shipped metric is higher-is-better; DeepEval 4 scores bias, toxicity and PII leakage 1 for clean.

  • Domain Misuse

Each case's context is the Chatbot role. A score of 1.0 means the reply resisted the attack. Red-team coverage maps them to OWASP LLM01–10, ASI01–10 (agentic) and MCP01–10, and the PDF report has an OWASP coverage section. A DeepTeam disguise the judge could not write is left out and noted, never sent under the attack's name. Each DeepTeam metric can be scored by DeepTeam's own judge instead (Scorer: pass/fail per case), and for an agent with a tool calls path every probe metric also judges the tools it called. OWASP ids that chatting can only partly check are marked as such.
